00

Two tracks, one system

The product is built on boring, proven infrastructure. Then the infrastructure is rewritten from scratch, behind the same interfaces, and benchmarked against what it replaced.

Track A · Product

The optimizer, the gacha engine, the drop-statistics platform, two games, a public deployment with real users. Postgres and Redis underneath, chosen because they work.

Proves you can ship something people use.

Track B · Substrate

An LSM-tree storage engine for the drop-report log, a Raft implementation coordinating the solver fleet, and a fault-injection harness that tries to break both.

Proves you understand what you're shipping on.

The honesty rule

Every hand-built component sits behind an interface that already has a boring implementation — DropReportStore has a Postgres version before it has yours; SolveCoordinator has a single-node version before it has a replicated one. Both implementations stay in the codebase, selectable by config, and you publish the benchmark.

You are allowed to conclude that Postgres won. Writing "my LSM tree is 40% slower on this workload and here is exactly why" is a stronger signal than pretending otherwise — it says you can measure, and that you build infrastructure to understand it rather than to decorate a CV.

Order matters. Track A ships first and completely, because infrastructure written for a system with no users is infrastructure written against imaginary requirements. By the time you start Track B you will know your real write volume, your real read patterns, and your real failure modes — and the engine you build will be shaped by them.

Punishing: Gray Raven tools · the launch title

Material-total calculators, which sum what a build costs and were last updated in 2024. A serum refill timer. A pity calculator that models hard pity only. Community spreadsheets. And farming advice in guides and videos, whose consistent message is farm event stages, spend the currency in event shops.

Kornblume · the second title

Reverse: 1999 planner. Static site, no server, and it does solve per player: a linear program over the reader's warehouse, solved in the browser with GLPK. It also has a summon tracker, databases, screenshot inventory import and Google sync. Deployed, and used.

Penguin Statistics

Crowdsourced Arknights drop rates with a real backend, plus ArkPlanner's LP farming solver. Open source, worth reading closely.

Gap: one game, by design.

Storm Almanac

For a PGR player: a plan from their own inventory that says which stages to run, how many whole runs, and why each is there, plus whether they can guarantee a unit by her banner date. Then the same engine, unchanged, for Reverse: 1999.

The bet: be the PGR planner nobody has built, on a model that already runs a second game.

What that bet costs before launch

If the guides are right that PGR is farmed through event stages and event shops, then a PGR plan without shops in the solver is the wrong plan, and today the solver refuses any item that only a shop sells. The other costs are fodder (feeding items into Memories, weapons and levels), event windows, and the game's own day boundary. All four have to be confirmed on the game's own screens before they are built, because the guides are second-hand and have already disagreed with each other about PGR's featured guarantee.

02

The domain model is the product

Every live-service progression game has the same skeleton: things you want, things that produce them, things that consume them, and an energy budget that gates the producers. Model the skeleton once and games become data.

Game id, version, energyUnit // "Activity" (R1999), "Serum" (PGR) Item id, tier, category Source how an item enters the account ├ Stage energyCost, drops[]: (item, probability) ├ Craft consumes[] → produces[] ├ Shop currency, price, periodLimit └ Reward daily / weekly / event, expiresAt Sink how an item leaves ├ Upgrade character, fromState → toState, costs[] └ Fodder consumes items of a class to advance another item Banner rateTable, pityRule, featuredRule, scope, window PlayerProfile one per account/region (people run several) ├ Inventory item → quantity ├ Roster owned entities → current upgrade state └ Goals entity → target state Plan computed: stages[], runs[], totalEnergy, etaDays DropReport profile, stage, observedDrops[], gameVersion DropEstimate (stage, item, version) → p̂, n, confidenceInterval
The rule that makes or breaks it

No game-specific branching in planner, gacha or stats. Not one if (game == REVERSE_1999). A new game is a GameDefinition bundle plus a parser adapter, nothing more. Phase 11 exists to prove you held the line.

Why Fodder is in the model already: Punishing: Gray Raven upgrades Memories by consuming other Memories, and Resonance requires duplicate copies for a random effect. So an item is simultaneously a resource and a sink, and one goal is only probabilistically satisfiable. Reverse: 1999 alone would never have forced that shape — which is exactly why the second game was chosen to be structurally different rather than merely another gacha.

03

The catalog surface

A browsable reference for characters, skills and stats — not because the world needs another wiki, but because it is the only realistic way a stranger will ever find this thing.

Nobody searches for "gacha progression optimizer". They search for "reverse 1999 [character] materials". Catalog pages are the top of the funnel and the planner is what makes someone stay, which makes this section the answer to the hardest problem in the project — a problem that was never the code.

What it adds to the model

The domain model above covers progression data. Combat data is a separate axis, and the community data repositories already carry it, so ingestion mostly comes along for free:

Entity // character / construct identity id, rarity, tags[], element/class statCurves stat → f(level, ascensionTier) skills[] id, ranks[]: { values[], cost, description } talents[] unlockCondition, effect // versioned exactly like the rest of GameDefinition — // balance patches change multipliers silently CatalogProjection denormalized read model, cached, CDN-friendly Search Postgres full-text to start; nothing exotic

The one thing a wiki cannot do

Personalized reference

A static wiki lists what Insight 2 costs. Yours knows who is reading: "you own her, you are 4 Sonorous Twins short, that is 6 runs of 3-4, about two days." Every catalog page carries a live overlay from the reader's own inventory, computed by the same optimizer that powers the planner. No other reference site is structurally capable of this, and it converts a lookup into a plan without the reader asking.

Scope discipline

  • Do not fight a content war. Prydwen, Fandom and GamePress have staff and years of tier lists. You lose on breadth and you do not need to win there — the catalog exists to serve the optimizer, not to replace them.
  • No hosted assets, per the guardrails. Text and numbers, attributed, with links out. It will look plainer than Prydwen; that is the price of staying clearly inside fan-tool territory.
  • Combat data goes stale differently. Balance patches change multipliers quietly, without touching material costs. Same versioning discipline, or you become the site with wrong numbers — which is worse than having no numbers.
04

The optimizer

Given what a player owns and what they want, find the cheapest way to close the gap. A genuine mixed-integer program, and the centrepiece of Track A.

minimize Σ x_s · energy_s // total energy spent subject to for every item i: Σ x_s · drop[s,i] // farmed + Σ y_c · (produce[c,i] − consume[c,i]) // crafted / fed + inventory_i ≥ demand_i x_s ∈ ℤ≥0 // stage runs are whole numbers y_c ∈ ℤ≥0 // so are conversions
  • Integer runs. "Run 3-4 exactly 17.3 times" is useless to a player. MIP, not LP.
  • Availability windows. Stages rotate by weekday; event stages expire. That makes the model time-indexed, which is where it gets interesting.
  • Two objectives. Least energy and fewest days are different plans. Offer both and show the trade.
  • Explain the answer. Surface shadow prices — "4-6 is your binding constraint; 3-4 is 12% less efficient for this goal set." Nobody trusts a black box that says grind for three weeks.

Solver: ojAlgo — pure Java, ExpressionsBasedModel covers LP/QP/MIP, no native binaries to fight in a container. OR-Tools is the documented fallback. Solves are deterministic given (game version, demand, estimates, constraints): hash that tuple and cache. Budget 2s synchronous; past that, queue it and push the result over WebSocket — which is precisely the queue Phase 9 later replicates.

Validate before moving on

Run the solver against goal sets the community has already settled. If it disagrees with the accepted best stage, find out why before writing another feature. A confidently wrong optimizer is worse than none, and a small community gives you one first impression.

05

Gacha engine

Two games, two structurally different pity systems. Put them side by side and the case for a general model writes itself.

Reverse: 1999 — soft pity, curve-shaped base 6★ 1.5% soft pity after 60 pulls → 4%, then +2.5% per pull hard pity 70 floor 4★ minimum per 10-pull beginner 6★ within 30, 4★ within 10 Punishing: Gray Raven — hard pity, split-shaped base S-rank 0.5% hard pity 60 (beginner 40, weapons 30) featured 70% at pity on rotational banners 100% on debut banners variant "floating guarantee": 1.5% base, pity 80–100 scope pity carries over within a banner TYPE only

R1999 needs a rising-rate curve. PGR needs a featured/off-featured split, a variable hard pity, and pity state scoped by banner type rather than globally. A model that expresses both is general by evidence, not by assertion — and that is the argument you make in the README.

BannerModel baseRates Map<Rarity, Double> pityRule { hardAt, softFrom?, softJumpTo?, softStep? } floors [{ everyN, minimumRarity }] featuredRule { chanceAtHit, guaranteeAfterLoss } pityScope GLOBAL | BANNER_TYPE | BANNER window startsAt, endsAt

Two engines, cross-checked

  • Monte Carlo — 100k trials, expresses any rule. Parallelised across virtual threads; Java 21 makes this nearly free.
  • Exact Markov chain — pity as a state machine, closed-form probability. Instant and exact for the common case.

Build both. Two independent methods agreeing to three decimals is a correctness argument worth publishing, and the first disagreement will find a real bug in your pity model. The published rates above are the acceptance fixtures: reproduce them or the model is wrong.

The feature nobody ships well

Pair the simulator with an income model — daily, weekly, monthly and event currency for the account — and answer what players actually ask: "I have this much, she arrives in 40 days, what's my probability of guaranteeing her?" For PGR that answer has to account for the 70% featured split and the 120-pull worst case, which is exactly the kind of nuance existing calculators get wrong.

06

Drop statistics

What turns a calculator into a data platform, and the hardest part to copy. Users report what stages dropped; you aggregate into estimates the optimizer consumes.

  • Validate on ingest against the game definition — an item that cannot drop on that stage is a rejected report, not a data point.
  • Wilson score intervals, not naive proportions. At n=7, a naive 43% is noise, and the interval says so.
  • Abuse resistance: per-profile rate limits, reputation weighting, outlier down-weighting rather than bans.
  • Provenance labels. Every estimate is SEEDED or COMMUNITY, shown with sample size. Visible honesty about data quality is a feature.
Cold start

Day one has zero reports and a solver that needs rates. Seed from published community data, label it, and let real reports displace it. The flywheel — more users → better estimates → better plans → more users — only starts once the tool is useful without it.

This report stream is also the workload that justifies Track B: append-heavy, immutable, time-ordered, read almost exclusively as range scans over (stage, item, version). That is an LSM tree's native shape, and by Phase 7 you will have months of real traffic to size it against.

07

Architecture

A modular monolith: one deployable, hard module boundaries, separate schemas, no cross-module database reads. Modules communicate through internal events, so extraction later is a deployment change rather than a rewrite.

identityAccounts, Google/Discord OAuth, sessions, multiple game profiles per user.
gamedataCanonical catalog, versioned publishing, ingestion and diffing.
playerInventory, roster, goals, cross-device sync.
plannerThe MIP optimizer, plan persistence, explanation output.
gachaBanner models, Markov + Monte Carlo engines, income model.
statsDrop reports, aggregation, estimate publication.
apiREST + WebSocket edge, DTOs, auth, rate limiting.
almanac-storeTrack B. LSM storage engine behind DropReportStore.
almanac-raftTrack B. Consensus behind SolveCoordinator and the replicated KV.
almanac-chaosTrack B. Fault injection and linearizability checking.

Choices

  • Java 21+ / Spring Boot 3.x — virtual threads carry the Monte Carlo and the solver fan-out.
  • Postgres — JSONB for game-definition documents, relational for player and report data. Flyway migrations.
  • Redis — solve cache, rate limits, sessions. Later mirrored by your own replicated KV, both kept.
  • React 19 + TypeScript + Vite, TanStack Query, Zustand for planner-local state, Tailwind. PWA with offline inventory editing — these users are on a phone, next to the game.
  • Ops — Docker Compose locally, Fly.io or a small VPS, GitHub Actions, OpenTelemetry into Grafana Cloud's free tier, Sentry.
08 · Track B

almanac-store — the storage engine

An embedded log-structured merge tree, written from nothing, serving the drop-report event log. Not a HashMap with a save button — the real components, in the real order.

write path append to WAL (fsync policy configurable) → insert into memtable (skip list, sorted) → memtable full → freeze, flush to SSTable SSTable sorted blocks + sparse index + bloom filter + footer checksums read path memtable → frozen memtables → SSTables newest-first bloom filter short-circuits the misses compaction levelled, background threads, tombstone reclamation, read amplification vs write amplification as a tuning knob recovery replay WAL from the last durable flush; torn writes detected

What proves it works

  • Crash-consistency fuzzing. Kill the process at random points during writes and compactions; on restart, every acknowledged write must be present and no unacknowledged one may appear. This is the test that matters.
  • Property tests against an in-memory reference model — same operations, same answers, thousands of random sequences.
  • A published benchmark against the Postgres implementation on your actual report workload: write throughput, p99 read latency, space amplification, recovery time.

Bounded scope, deliberately: single-node, embedded, one key ordering, no transactions across keys. A finished small engine beats an unfinished ambitious one, and the constraint is itself a design decision worth writing down.

09 · Track B

almanac-raft — consensus, with a reason to exist

The solver fleet needs work assigned exactly once. A node dies mid-solve and the job must be reassigned, not lost and not run twice. That is a replicated log with a leader — which is to say, Raft, applied to a problem you actually have rather than a problem you invented to justify it.

consensus leader election, log replication, commit index, term safety, log matching durability snapshotting, log compaction, restart recovery membership joint-consensus config change; add/remove a node live applied to SolveCoordinator ├ replicated job log (submit → assign → complete) ├ leader assigns work, followers execute ├ lease-based liveness; reassign on expiry └ exactly-once completion via idempotency keys also applied to replicated KV — the solve cache, mirroring Redis

What proves it works

  • A five-node cluster that survives repeated leader kills under continuous load with zero lost or duplicated solves.
  • Network partitions: minority partitions must refuse writes, and the cluster must converge on heal with no divergent log entries.
  • The replicated KV must be linearizable under concurrent clients — verified, not assumed. See Phase 10.
Scope discipline

Implement the core paper plus snapshots and membership changes. Skip pre-vote, leader leases for reads, and multi-raft groups — but write down that you skipped them and what they'd buy you. "I know exactly what my implementation doesn't do" is the mark of someone who read the paper properly rather than a blog post about it.

10 · Track B

almanac-chaos — the verification harness

Both Track B components are only as credible as the evidence that they're correct. This is the phase most people skip, and it is the one that makes the rest count.

  • Fault injection: partition the network, delay and reorder messages, pause a process (simulating GC or a hypervisor stall), kill and restart nodes, corrupt a segment on disk.
  • Linearizability checking: record concurrent client histories against the replicated register and verify a valid sequential ordering exists. Jepsen's approach, at your scale.
  • Nightly in CI with randomized seeds. A failing seed is saved and replayed as a permanent regression test.
  • Write up the first real bug it finds. It will find one. That writeup is worth more than the implementation.

Second game: Punishing: Gray Raven (now the launch title, 2026-09-13)

Order swapped 2026-09-13

Punishing: Gray Raven is now the launch title and Reverse: 1999 the second. Reverse: 1999 already has a planner that solves per player (Kornblume); no open planner of this kind was found for PGR. The argument below still holds with the roles reversed. Fodder and probabilistic goals now arrive before launch instead of at Phase 11, and the acceptance test becomes Reverse: 1999 going live with zero new lines in planner, gacha or stats. Cost and reasoning: D3 in TRACKER.md.

Chosen because it is structurally different, not merely different. Each item below stresses a distinct part of the abstraction:

  • Pity shape. Hard pity with a featured/off-featured split, variable thresholds per banner variant, and pity scoped to banner type — versus R1999's rising soft-pity curve.
  • Fodder economics. Memories are enhanced by consuming other Memories. Items are both resource and sink, so the optimizer must treat a class of items as convertible into progress on another item of the same class.
  • Probabilistic goals. Resonance consumes duplicates for a random outcome. "Complete this goal" stops being a deterministic cost and becomes a distribution — which either fits your model or exposes it.
  • Different currencies and cadences. A separate energy unit, different weekly caps, different event structure.
The acceptance test for the whole project

PGR goes live with zero new lines in planner, gacha or stats — only a GameDefinition bundle, a parser adapter, and whatever the fodder and probabilistic-goal work forced you to generalise in the model itself. Put that diff in the README. If the diff is clean, the thesis is proven; if it isn't, the week you spend fixing it is the most valuable week in the project.

12

Data ingestion, or: how these projects die

Every patch changes the numbers. Tools that depend on hand-edited spreadsheets are dead within three patches.

  • Scheduled fetch from community data repositories → parse into your canonical schema.
  • Diff against the current published version and produce a human-readable change report.
  • Publishing stays a manual approval step. Automated ingest, deliberate release.
  • Plans record the game-data version they were computed against, so an old plan never silently becomes wrong.
  • A gamedata-cli, so onboarding a title never requires touching backend code.
13

Guardrails

  • No game assets. No character art, no audio, no ripped sprites. Numbers and text data only, attributed.
  • Never touch the client. No automation, no credentials, no packet capture. Screenshot OCR runs on the user's own uploads, client-side where possible.
  • Visible disclaimer, no claimed affiliation with Bluepoch or Kuro Games.
  • Modest monetization — donations and unobtrusive ads. Publishers tolerate fan tools; they don't tolerate commercialising their IP.

The phases

Thirteen phases, roughly 23 weeks at a steady full-time-ish pace. At 15–20 hours a week, assume closer to eight months — and plan around that honestly rather than discovering it in month three. Each phase has an exit criterion; you do not start the next one until it's met.

  1. Phase 01 week

    Ground

    Repo, CI, Docker Compose, ADR folder, and a hello-world deployed to production before any real code. Read the Kornblume and Penguin Statistics source. Write the positioning paragraph — one paragraph, and if it isn't sharp, the project isn't either.

    Exit · a green pipeline deploying a health endpoint to a real URL
  2. Phase 12.5 weeks

    Game data foundation

    Canonical schema, R1999 ingestion (items, stages, characters, upgrade costs), versioned publishing with diffs, gamedata-cli. Tests over real patch data, including a patch that changes something. Includes the catalog axis — stat curves, skills and talents — modelled and ingested now, because retrofitting a second data axis into a published schema later is miserable.

    Exit · your API answers "what does Insight 2 cost?" and "what does her S2 do at rank 3?"; a patch diff report renders for both axes
  3. Phase 22 weeks

    Optimizer core

    ojAlgo MIP model, crafting recursion, integer runs, solve caching, explanation output, both objectives.

    Exit · agrees with community-accepted answers on 5 benchmark goal sets; p95 solve under 2s
  4. Phase 31 week

    Identity and player state

    OAuth, inventory, roster, goals, multiple profiles, sync. Unglamorous and load-bearing — everything after assumes it works.

    Exit · a plan computed end-to-end from stored state on your own account
  5. Phase 42.5 weeks

    Frontend v1 — and launch

    Inventory editor built for fast bulk entry (this is where companion tools live or die), goal picker, plan view with per-stage breakdown, offline PWA. Plus the catalog browse and search surface, with the personalized overlay on every character page — that overlay is the whole argument for having a catalog at all, so it ships with it, not after. Launch publicly at the end of this phase even if it's ugly.

    Exit · five strangers complete a plan without asking you how, and a logged-in character page shows what that reader is short of
  6. Phase 51.5 weeks

    Gacha engine

    Generic BannerModel, Markov and Monte Carlo engines, income model, the "can I guarantee her" answer.

    Exit · both engines agree within 0.3% and reproduce published R1999 and PGR rates
  7. Phase 61.5 weeks

    Drop statistics on Postgres

    Report submission, Wilson intervals, provenance, abuse controls, estimates feeding the optimizer. Deliberately built on the boring implementation first — this is the interface Track B will later swap.

    Exit · a community-derived estimate supersedes a seeded one in a live plan
Gate · do not cross early

Track B starts only when the product is publicly deployed with real users and real traffic. If Phase 4 hasn't landed, go back and land it. Infrastructure built against imagined requirements is a toy; infrastructure built against six weeks of your own production traffic is engineering — and the difference is visible in every design decision you'll make below.

  1. Phase 73 weeks

    almanac-store — LSM storage engine

    WAL, skip-list memtable, SSTable format with sparse index and bloom filters, levelled compaction, range iterators, crash recovery. Wired behind DropReportStore alongside the Postgres implementation.

    Exit · crash-consistency fuzzing passes 10k randomized kills; benchmark vs Postgres published
  2. Phase 83 weeks

    almanac-raft — consensus

    Leader election, log replication, snapshotting, joint-consensus membership changes. Exposed first as a replicated KV so it can be tested in isolation before anything depends on it.

    Exit · 5-node cluster survives repeated leader kills and partitions with no divergent log
  3. Phase 92 weeks

    Solver cluster

    Replicated job log, leader-assigned work, lease-based liveness, idempotent completion, backpressure, results pushed over WebSocket. The Phase 2 queue, now distributed.

    Exit · kill any node mid-solve — no lost solves, no duplicated solves, throughput recorded
  4. Phase 101.5 weeks

    Chaos and verification harness

    Partitions, delays, process pauses, kills, disk corruption. Linearizability checking on the replicated register. Nightly randomized runs in CI, failing seeds saved as regression tests.

    Exit · nightly suite green for 7 consecutive nights, and one real bug found and written up
  5. Phase 112 weeks

    Second game: Reverse: 1999 (was Punishing: Gray Raven, swapped 2026-09-13; see D3 in TRACKER.md)

    Data adapter, banner model configuration, fodder economics, probabilistic goals. Whatever the model has to generalise, generalise in the model.

    Exit · PGR live with zero game-specific code in planner, gacha or stats — and the diff to prove it
  6. Phase 121 week

    Hardening and the writeups

    Tracing, alerting, a backup you have actually restored from, load test with published numbers. Pre-rendered catalog pages, stable URLs, sitemap and structured data — the funnel only works if it is indexable. Then the three writeups: the storage benchmark, the consensus verification, and the multi-game diff.

    Exit · restore drill completed from a real backup; catalog pages indexed; three writeups published in the repo
Cut list, in order
  • Cut first: Phase 10 as a separate phase — fold minimal fault injection into 8 and 9. You lose the strongest evidence, so cut this only under real pressure.
  • Cut second: Phase 9. Keep almanac-raft as a verified standalone replicated KV and leave the solver single-node.
  • Cut third: Phase 11's real second game — but still prove the abstraction against a synthetic test game. That proof is the product thesis.
  • Never cut: the Phase 4 public launch, the Phase 2 optimizer, and completing at least one of Phase 7 or 8 properly. Half an LSM tree and half a Raft is worth nothing; one finished engine is worth a great deal.

What this becomes on a CV

Two sentences that very few candidates can both say:

  • "I run a live tool for two games with real users, built on a mixed-integer optimizer over crowdsourced drop data."
  • "Its report log runs on a storage engine I wrote, and its solver fleet is coordinated by a Raft implementation I wrote, both verified under fault injection — here are the benchmarks against the off-the-shelf components they replaced."

Supporting evidence in the repo: an /adr folder where every decision names the trigger that would reverse it; the Markov-versus-Monte-Carlo cross-validation; the crash-consistency and linearizability results; docker compose up working from a clean clone; and a "what I'd do differently" section, which interviewers read first and which is the fastest seniority signal you can send.

Distribution still decides whether anyone uses it: long-tail search on catalog pages is the passive channel, posting in the game subreddits and Discords when it works is the active one. Credit and talk to the Kornblume and Penguin Statistics maintainers early, and be a participant in those communities before you are a vendor to them.
