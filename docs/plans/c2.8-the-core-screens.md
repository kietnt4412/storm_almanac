# C2.8 · The five core screens, made to show what they know

**Status:** scope agreed 2026-10-01 (fifty-ninth): the maintainer took **all
five, in the recommended order**. **Mockups agreed 2026-10-01 (sixtieth)**, all
five as shown, with the recommended answer to each question below. Part of
Track C's C2, so C2's exit applies: every screen driven at 375 and 1280 px, and
a self-run rehearsal with no stall left.

## The data questions, answered from the code (sixtieth)

1. **A reward's cadence is on no route the plan page reads.** `/measures`
   carries it for a reward behind a measure (`MeasureBar.cadence`), which is
   every PGR reward today, but a reward with no measure would be missed. The
   model counts the k-th claim of a weekly at day 7k (`Cadence.occurrencesIn`,
   `days / 7`), not on a calendar date, so the bar marks days 7, 14, 21 and
   28, never weekdays. `etaDays` is `max(totalEnergy / energyPerDay,
   daysNeeded)`, so the binding half can be read off what the page holds.
   **Agreed:** an optional `cadence` on each reward line of the plan.
2. **The score per stage is not on the wire.** `StageRunView` is runs, cost
   and energy. **Agreed:** an optional field for what each stage's runs pay,
   from the yields the solve used, not re-read from the bundle (a sampled
   yield is discounted by ADR 0011, and the page must not undo that).
3. **Inventory's "plan uses" is purchases only** (`usesOf`: a conversion's
   `spends` and `boughtItem`). Set against the bag, it would call Simulation
   Score 3,362 short when the plan farms it. **Agreed:** the ring compares the
   bag with **the demand the solver resolved** (gates in, crossed states out),
   a new optional field on the plan. "Farmed by the plan" is its own state,
   not "short".
4. **Covered is a fixed green token, `--ok`**, which no game palette
   redefines, like the rarity colours: under PGR's crimson, covered and short
   were both red.

## Why

The maintainer asked for the core pages (inventory, roster, goals, plan, pulls)
to be "even more impressive". Each page already holds numbers it only states
as text or a dropdown. The work is to **draw what the page already knows**. It
is not to invent decoration, and not to claim something the solver does not
say.

## Two rules that hold for every item

1. **No game art** (CLAUDE.md). No portraits or item icons; shapes, type and
   numbers only, drawn as SVG and CSS like `ChanceCurve` and `SpendBar`. No new
   chart library, which would also mean fighting E1 for the download.
2. **Draw nothing the plan does not claim.** The plan has **no day-by-day
   schedule** ([ADR 0013](../adr/0013-the-horizon-is-a-scalar-not-an-index.md)),
   so no calendar says "run this on Tuesday". It does not say which run pays
   for which goal, so nothing draws a stage → goal line (the same rule as
   C2.6's circuit). Every new picture must have its numbers said in words on
   the same screen, and be `aria-hidden` if it adds none.

## The five, in build order

### 1 · Goals: ladder sliders with a live cost

- **A segmented ladder per track** in place of the target dropdown. It runs
  from the roster's state to the track's last state, and the target is dragged
  along it. Promote shows its rank names as pips (the step's `toName`, ADR
  0032); skills show their levels. It must be keyboard-operable (arrow keys
  move the target), and keep the dropdown's label for a screen reader.
- **Cost of the chosen range, live**, under each track ("Red Orb 4 → 18 ·
  41 Skill Point · 197,000 Cogs") and summed for the goal. Data: the
  upgrades route (`UpgradesResponse.steps`: `costs` and `progress` per step),
  already fetched for the track names. **A client-side sum, not a solve.**
- **Say what the sum leaves out**, because it is not the plan:
  - a step with several prices (ADR 0021) is shown as "one of", not added;
  - a gate (ADR 0019) is demand the resolver adds, so it is not in the sum;
  - a state crossed by the roster (ADR 0026) is free.
  The line reads "the steps' own prices; the plan works out the cheapest way".
- **Drag to reorder priority**, with numbered badges, keeping ↑ ↓ for the
  keyboard. Goals have no PATCH (an ordered list has no per-key merge), so a
  reorder sends the whole list, exactly as ↑ ↓ does now.
- **Tests:** the sum over a range, a choice step not summed, a crossed state
  free, keyboard movement, and a reorder sending the list.

### 2 · Plan: why it takes this long, and where the energy goes

- **"Why 28 days?"** The horizon as one bar, with each claim of a cadenced
  reward marked (the Cage's four weekly claims). Under it, the energy the plan
  needs as a fill: `totalEnergy / energyPerDay` = about 8 of 28 days. At a
  glance, the weekly is what binds, not serum. Data: `etaDays` and
  `totalEnergy` on the plan, `energyPerDay` on the saved request, and
  `rewards[].times`. **Open: where a claim sits in the horizon** needs the
  reward's cadence and the game's `dayBoundary`. `/api/games` has the
  boundary; check whether the cadence is on a route the page can read. If
  not, add it as an optional wire field rather than hard-coding "weekly".
  When energy *is* what binds, the bar says that instead. Both cases need a
  test.
- **Resource flow (a Sankey diagram):** serum → each stage's runs → the
  currency they pay → each purchase → what it buys. Widths come from
  `stages[].totalEnergy` and `conversions[].spends` (`quantity`,
  `boughtItem`, `boughtQuantity`). With one stage the score earned equals the
  sum of what is spent (41 × 82 = 3,362). **With several stages, the score
  per stage is not on the wire**: check first, and add a field rather than
  guess a split. It stops at items and never reaches goals (rule 2).
- **"What's precious":** `shadowPrice` as horizontal bars, energy per one
  more of each item, zeros folded into the one sentence S10 already writes.
- **Tests:** the bar in both binding cases, flow widths summing to the plan's
  totals, and zero prices not drawn.

### 3 · Pulls: a pity dial, chance by date, copies

- **Pity dial:** a half-circle gauge from 0 to the wall (60), with the
  guarantee notched and the reader's counter filled. Data: `Odds.pity`, and
  the banner's wall. A drawn wall (ADR 0023) shows its range as a band, not
  a notch.
- **Chance by date.** The x-axis is days until the banner closes, which is
  the question the page exists for. **This needs the server**: `curve` is per
  pull count, and pulls per day come from the income model. Add an optional
  `byDay: {day, pulls, chance}[]` to `/pulls`, computed from the same
  `DeclaredIncomeModel` and chain in one call. Never make N calls from the
  page. A `gacha` change, so `GameAgnosticismTest` applies.
- **Copies breakdown:** the chance of exactly 1, 2, … copies as stacked bars.
  The chain answers "at least k"; exactly k is the difference of two of
  those. Also needs a field, `byCopies`, from the same call. Copy exchanges
  are not modelled (N38), and the chart's caption says so.
- **Tests:** backend, `byDay` agreeing with `chance` at `days` and
  `byCopies` summing to at most 1; frontend, the dial's fill and the band.

### 4 · Roster: a card per construct

- **Each track as a mini ladder**: Level as a bar to its cap, Promote as rank
  pips, each skill as its levels in dots, filled to the reached state. Overall
  completion is a ring, counting steps reached over steps in all tracks. Data:
  `RosterResponse` and the upgrades route's steps.
- **Hovering or focusing a step not yet reached** shows its price, the same
  numbers as Goals' sum.
- **Tests:** the fill from a roster with crossed states, and the ring's
  count.

### 5 · Inventory: coverage, and what is short

- **A coverage ring on each tile**: held against what the saved plan uses,
  green when covered and the plan's colour when short. **Check first what
  "uses" means** in `Inventory.tsx` (it already shows "plan spends" and "plan
  buys", line ~171). Use the same numbers, and do not invent a second idea
  of need.
- **A summary strip**: "covers 18 of 25 · 3 short", with filter chips: *Short
  for the plan*, *Used by the plan*, *Not used*. They sit beside today's
  "Only what I hold".
- **Small motion**: a number counts up when it changes, and a dot on the tile
  shows saved or waiting in the outbox, from the existing sync state.
- **Tests:** ring maths, filter chips, and the pending dot driven by the
  outbox.

## As built

### 1 · Goals (2026-10-01, sixtieth)

- **`LadderSlider`** (`roster/LadderSlider.tsx`) replaces the target dropdown:
  a native range input drawn over, so arrows, Home and End move it and a
  screen reader hears the old label with the state's name as its value. A
  value between two targets snaps forward; back to where the reader stands
  means "leave as is". Families of rank names ("Elite ★1", "Elite ★2") label
  the rail, worked out from the labels alone, so no game's ranks are known.
- **`rangeCost`** (`roster/rangeCost.ts`) sums the steps between where the
  reader stands and the target, EXP first: a step sold at several prices is
  named, never added; crossed states are never charged; gates are said not to
  be in it. On the rehearsal account Red Orb 4 → 18 reads **41 Skill Point ·
  197,000 Cogs**, the figure sequence 15 was read to.
- **The row's sum** sits under its tracks, with the line saying what it
  leaves out. **Drag to reorder** by a grip, numbered badges; ↑ ↓ stay for the
  keyboard and for touch, where HTML drag and drop does not fire.
- An overtaken target has no ladder (its end is behind the reader) and gets
  a *Clear* button in place of the dropdown's "(reached)" option.
- **Driven** on `rehearsal-s6` at 1280 px light and 375 px dark: End then
  three ← lands on Ace ★2 and the cost and sum follow; no horizontal overflow.
  Frontend 150 tests.

### 2 · Plan (2026-10-01, sixtieth)

- **Three optional wire fields**, each from the solve, never re-derived:
  `stages[].pays` (per run and total, off the `YieldTable` the solve used, via
  `Explanation.yields`), `rewards[].cadence`, and `needs` (the resolved
  demand, via `Explanation.demand`; page 5 reads it). `Explanation` keeps a
  four-argument constructor, so its other callers are untouched.
  `AuthoredBundlePlanTest` pins all three on the real bundle: 5 runs pay
  410 Simulation Score at 82 a run, Seeker System 1 → 18 needs 206,000 Cogs
  and 44 Skill Point, and every Cage tier is `WEEKLY`.
- **"Why N days?"** (`ui/WhyDays.tsx`): which half of `etaDays` binds,
  read off `totalEnergy ÷ energyPerDay` against `etaDays`; a weekly claim
  marked at day 7k, as the model counts it. The rate is the saved request's,
  or the one the last run was asked with, never the form's live value.
- **Where the energy goes** (`ui/PlanFlow.tsx`): per currency, stages →
  currency → purchases, both sides summing to the plan's numbers, with
  *From your bag* or *Left over* when they differ. It replaces the spend bars,
  which stay for a plan saved before `pays`. On a phone it keeps a readable
  size and scrolls inside its card; the caption says it in words.
- **What's precious**: the non-zero prices as bars against the dearest; zeros
  stay in S10's sentence.
- **A second local stack** (`web-alt` on 5174, `api-alt` on 8081,
  `frontend/vite.alt.config.ts`), because another session held 5173 and 8080
  and the new fields needed a backend running this code.
- **Driven** on `rehearsal-s6`: its saved plan (from before `pays`) showed the
  fallback; re-run with the same request, the bar reads "spent by day 8 … 4
  weekly claims … day 28" and the flow 3,362 Score → 2,472 / 545 / 345, i.e.
  74 / 16 / 10%. 1280 light and 375 dark, no page overflow. Every shadow price
  on that plan is zero, so its bars were proven by the unit test only.
